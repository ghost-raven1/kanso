# Подготовка сложных приложений к миграции

Этот документ разделяет готовые контракты и предстоящую работу. Пакеты Kanso исполняются на Solid; совместимость с React runtime и React-библиотеками не добавляется. Полная миграция приложения включает портирование его UI и проверку поведения.

## Фреймворк общего назначения

Аудиты реальных приложений задают требования и приоритеты, но не определяют
предметную модель Kanso. Основные типовые сценарии должны решаться общими API;
особые сценарии — их композицией или необязательными интеграциями.

- Ядро отвечает за язык компонентов, реактивность, Context, ownership и DOM.
  Веб-слой — за маршруты, данные, формы, SSR, SEO и жизненный цикл запросов.
- Оверлеи, темы, editor/motion, внешние stores, микрофронты и workers подключаются
  по необходимости. Их транспорт и поставщик задаются через явные контракты;
  приложение без интеграции не получает её runtime.
- Бизнес-сущности, роли, правила доступа, API endpoints, процессы и оформление
  принадлежат приложению. Ядро не содержит проверок конкретного проекта,
  известных route ID или его схемы данных.
- Общая абстракция появляется из повторяющегося поведения. Для крупного нового
  API нужен нейтральный пример основного сценария и существенно другой сценарий
  с тем же контрактом: например, защита черновика в профиле и редакторе статьи,
  подтверждение действия и форма внутри модального окна. Варианты задаются
  композицией и callbacks, а не исключениями под пример.

Покрытие оценивается по сценариям, а не по числу устранённых диагностик. Для
каждой группы требований фиксируются статус, исполнимый пример, ограничения и
способ реализации: общий API, необязательная интеграция или прикладной код.
Невозможность реализовать нужный сценарий без изменения ядра остаётся блокером;
необходимость написать бизнес-логику или перенести React-библиотеку не означает,
что её предметный API должен стать частью фреймворка.

## Готово в 0.6.1

- Аудит нескольких entries/configs, цепочек Vite re-exports и локальных ESM source packages; явный отчёт охвата и блокировка записи при неполном анализе.

## Следующие этапы

Цель 1.0 — техническая готовность фреймворка к полному переносу сложного
приложения. Сам перенос, изменение исходников приложения и его развёртывание
в эту работу не входят. Критерии ниже проверяются на нейтральных fixtures;
готовность конкретного приложения впоследствии подтверждается отдельно.

| Приоритет | Что подготовить | Проверяемый результат |
| --- | --- | --- |
| P0 | Доступные overlay primitives поверх Portal и темы через CSS variables | SSR, обе темы, keyboard/focus trap/return, scroll lock, touch, вложенные окна; без скрытого React и без обещания MUI clone |
| P1 | History/search/scroll и dirty navigation guard; контроллер форм для существующего HTTP API | Back/forward и replace сохраняют ожидаемый URL/state; draft не теряется; validation/reset, upload progress/cancel и частичные ошибки проверены |
| P1 | Внешняя invalidation HTML-кеша и прикладные cancellable subscriptions | Событие backend сбрасывает нужный кеш; поздний результат не восстанавливает закрытую страницу; cookie/session state остаётся в request scope |
| P1 | Инструменты портирования federation exposes/shared contracts и расширения native Service Worker events | Старый документ использует закреплённый выпуск; обновление не теряет draft; retry/rollback не исполняет action другой версии |
| P2 | Обёртки editor/motion и оставшиеся специализированные UI-контракты | Реальные пользовательские операции, cleanup, accessibility и формат данных сохраняются |

Это очередь разработки, а не доступные API. Имена будущих lifecycle/UI функций нужно закреплять исполнимой спецификацией перед реализацией. Существующий `createStore` сохраняет контракт Solid; стороннее хранилище подключается отдельным binding. Политику auth, прав доступа, replay offline-мутаций и транспорт backend определяет приложение.

## Первая вертикальная приёмка

Подготовить нейтральный SSR-пример «список публикаций → статья» с loader, SEO, общими settings, изображениями и независимым remote. Затем добавить каталог и форму с незавершённым draft. Большой редактор не должен быть первым проверочным приложением.

Для каждого примера: исходный HTML с данными/SEO, empty/error/404/redirect, back/forward, сохранение DOM и ввода при гидратации, отсутствие повторного initial loader, изоляция параллельных запросов, отмена подписок и поздних ответов. Remote A/B/rollback проверяются без пересборки оболочки. Установка выполняется из npm pack вне workspace; TypeScript, production build и Chromium/Firefox/WebKit обязательны. Оценки производительности публикуются только после измерения.

Первый этап не требует переноса конкретного стороннего приложения. Материалы частных обследований, исходники и предметные данные в публичные fixtures не включаются.

## Условия готовности 1.0

В 0.10.0 реализованы [Dialog](dialogs.md) для редактора и вложенного подтверждения,
[lazy-загрузка страниц и интерактивных блоков](lazy.md), [useTransition](transitions.md)
с настраиваемой анимацией. Тема окна задаётся обычными CSS variables; полноценная система
design tokens, сложные navigation guards и внешний form controller остаются в очереди.
Усиленные границы HTTP/кеша описаны в [руководстве безопасности](security.md).

1. Для каждой выявленной зависимости от React есть проверенный способ
   портирования на Kanso, vanilla или Solid. UI, маршрутизатор, editor/motion,
   тесты и federation описаны отдельно; библиотечные заглушки не считаются портом.
2. В нейтральных примерах воспроизведены используемые типы, hooks и JSX. Мигратор
   разрешает весь выбранный граф, сохраняет диагностики изменённой семантики,
   блокирует запись при несовместимости и идемпотентен после разрешённых правок.
3. Проверены сложная навигация, сохранение/отмена draft, формы существующего API,
   оверлеи, общие настройки и жизненный цикл внешних subscriptions. Для каждого
   неподдержанного контракта указана проверяемая замена или остаётся блокер 1.0.
4. SSR, SEO, request isolation, гидратация, авторизованные данные в service scope,
   кеш-инвалидация, ошибки и отмена проверены без утечки состояния и повторных
   мутаций. Backend, auth и права доступа остаются ответственностью приложения.
5. Независимые remote-выпуски, shared contracts, обновление/откат и Web/Service
   Workers проходят production-сценарии; старые документы не вызывают чужие actions.
6. Установка из `npm pack`, TypeScript, compiler/migrator/HMR/SEO проверки и
   Chromium/Firefox/WebKit проходят в CI на итоговом SHA. Производственный граф
   не содержит React, тестовый код и HMR не попадают в обычные приложения.
7. Крупные API проверены на разных прикладных сценариях без проектных условий
   в ядре. Основные группы требований покрыты общими возможностями; для остальных
   есть проверяемый путь через композицию или интеграцию. Необязательные модули
   не увеличивают runtime приложения, которое их не использует.

Версию 1.0 нельзя объявлять готовой только по числу зелёных unit-тестов или
отсутствию ошибок синтаксиса: очередь выше должна быть закрыта контрактами,
примерами и воспроизводимыми сценариями. Завершённая миграция конкретного
приложения не является результатом этой задачи.
